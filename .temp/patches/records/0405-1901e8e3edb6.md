## Source intent
Security-policy consistency fix: `-f` (force) only suppresses the prompt — it
does not add destructiveness, so `rm -r /` and `rm -rf /` are equally
destructive (especially under `sudo`, where there is no prompt to suppress).
The patch therefore:
1. Removes the force-flag lookahead from `RE_D_RM_RF_ROOT`
   (`(?=[^|;]*\s(?:-[A-Za-z]*f[A-Za-z]*|--force)(?=\s|$))`), making the raw
   layer's protected-root risk gate depend ONLY on the recursive flag.
2. Removes the `(?=.*\s-Force\b)` lookahead from
   `RE_D_PS_RECURSIVE_DELETE_ROOT`, aligning the raw Remove-Item branch with
   the token layer (classifyTokens already checks only `-recurse`) so sudo
   wrappers cannot short-circuit an unforced `Remove-Item -Recurse /`.
3. Renames `hasRecursiveForceDeleteFlags` → `hasRecursiveDeleteFlags` and
   drops its force clause; classifyTokens' rm branch comment and cautious
   reason string update; plain `rm` still falls back to cautious via
   FILE_DELETE_COMMANDS.
4. Adds 3 test blocks: protected-root dangerous matrix (short/long recursive
   flags, wrappers bash -c / ssh / wsl / $() substitution / unknown prefix
   "task rm"), non-protected + force-only cautious guards, and
   `Remove-Item -Recurse` without -Force dangerous.
