## 2. Upstream design
TUI session route (`packages/tui/src/routes/session/index.tsx`) computes `pending` = incomplete assistant message ID used by `UserMessage` for **QUEUED** chrome (`props.pending && message.id > pending`).

V2 already selects incomplete assistants relative to the last **completed** assistant id (stronger than SMARK’s original simple findLast). Session status lives in `sync.data.session_status[sessionID]` (`idle` | `busy` | `retry`); server often **deletes** the map entry when idle, so missing status means idle.

## 3. SMARK source design
Before scanning messages for incomplete assistants:
```
const status = sync.data.session_status?.[route.sessionID]
if (!status || status.type === "idle") return undefined
```
Stops idle sessions from showing QUEUED chrome based on leftover incomplete assistant rows, and avoids idle memo work that tracks the full message list.

## 4. Target adaptation
Apply the same gate **before** the existing V2 completed-id filter in the `pending` memo. Owner path moved from `packages/opencode/src/cli/cmd/tui/routes/session/index.tsx` to `packages/tui/src/routes/session/index.tsx`. Chinese comment at the gate.

## 5. Why keep V2 completed-id scan
Upstream selection is more precise. SMARK gate is orthogonal: “do not compute pending at all when idle.” Combining both preserves upstream strength and SMARK idle contract.

## 6. Call chain
1. Server publishes `session.status` events (idle deletes map entry; busy/retry set type).
2. TUI `sync` store updates `session_status[sessionID]`.
3. Session route `pending` memo reads status then optionally scans `messages()`.
4. Each `UserMessage` uses `pending` to decide QUEUED badge via id comparison.
