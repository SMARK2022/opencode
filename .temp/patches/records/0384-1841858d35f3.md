## Source intent

`QuestionPrompt` (`question.tsx`) and `DialogPrompt` (`dialog-prompt.tsx`) render
the voice recording footer status via
`PromptVoiceInput.voiceInputStatusText(voiceInputStatus(), voiceShortcut() || voiceShortcutFallback)` —
without a third `now()` argument and without any `createRefreshClock`-driven
periodic refresh. The mechanism: during steady-state recording,
`voiceInputStatus()` no longer changes, so the inline JSX expression has no
reactive dependency that re-evaluates; the `now` argument (when present) is
evaluated only once at recording-start instant, and the timer display freezes at
00:00 forever. The main Prompt already had the proven pattern
(`createRefreshClock(() => running() || voiceInputStatus().type === "recording")`
+ `now()` passed into `voiceInputStatusText`).

Fix per component:
1. `import { createRefreshClock } from "../../util/signal"`.
2. `const now = createRefreshClock(() => voiceInputStatus().type === "recording")`
   right after the voice shortcut signals.
3. Pass `now()` as the third argument at the footer call site.
4. The test file gains a `createRefreshClock` behavior-contract test (active ticks
   / inactive stops / dispose cleans up the interval). This util previously had
   zero test coverage; the contract lives at 10ms interval via `createRoot`
   isolation so real 1s waits are avoided. Every DialogPrompt consumer (Goal
   create/edit, Session rename, Provider config, Plugin API) is fixed implicitly.
