## 三方比较与适配决策

1. **db 参数线**：目标 ColdStorage 自 #524 起要求 `TxOrDb` 显式传参（source 用全局路径）；全部执行域函数签名带 `db`，语义与 source 逐行对齐（executeMaintenance/executeCompression/runVacuum/waitForDaemonTask/taskResult/vacuumResult 逐 hunk 对照 original L1591-1764 核验）。
2. **printMaintenance 通道迁移**：目标基线为 `console.log`（stdout）；source 为 `UI.println`（stderr）且 source 测试断言 stdout 为空、JSON 在 stderr。本 patch 对齐 source：`UI.println(JSON.stringify(...))`，stdout 保持单值协议。#524 既有断言 `stdout || stderr.slice(indexOf("{"))` 兼容两个通道，不需回改。
3. **#524 status 测试 WAL 适配**：400k 行单事务夹具产生 ~59MB WAL，CLI 打开库时 stderr 前缀 `large WAL file detected — recovering… {…}`，其 `{` 被 `indexOf("{")` 误命中（JSON 移到 stderr 后混流）。夹具在 close 前 `PRAGMA wal_checkpoint(TRUNCATE)` 消除恢复日志；断言与扫描量不变（复现脚本 D:/Temp/opencode/sdiag535b.ts，STDERR_HEAD 直接观测到混流根因）。
4. **detach 测试超时**：recovery 前置是 source 有意的启动顺序变化，daemon lock 发布延迟；"Windows daemon detaches" 测试原无显式 timeout（bun 默认 5s）在全量并发下被顶穿。补显式 30_000（与其余 lifecycle 测试同档），断言不动。
5. **sameOwner 类型谓词**：0535 重写比较体后 TS18048（current possibly undefined）；恢复 `current is ServerLockInfo` 谓词（#523 期先例），行为零变化。
6. **不移植 hunk（残差）**：original L2037-2090 的 index.ts quietDbMigration 门与对应测试 "does not classify a run message containing db status as a database command"（断言 stderr 含 "Performing one time database migration"）。目标 v1.18.32 无 CLI 一次性迁移展示层（grep src 无该文案；migration 由 core 内联执行，无 presentation owner）——属上游架构演化后 owner 消失，恢复该门会引入第二迁移展示层。record 披露，产品行为无缺失（machine JSON 纯度由 T2 直接覆盖）。
7. **#pty → @lydell/node-pty**：目标无 `#pty` imports 条目；root 依赖 `@lydell/node-pty@1.2.0-beta.12` 已装（workspace hoist），直接 import，API（onData/onExit/write/kill）同构。

## 最终行为

daemon 在场时 human compress 依次呈现 owner 警告→Y/N；Y 经 maintenanceIdle 停机→offline 压缩（pulse/汇总）→可选 reclaim vacuum；N 经 control 轮询完成且不再请求物理回收；machine 域 `--vacuum --yes --json` silent-stop 后单 JSON。conditional shutdown 在 pending/active/terminal-but-active 三窗口一律 409，普通 stop 语义不变；daemon lock 只在 recovery 完成登记后发布。
