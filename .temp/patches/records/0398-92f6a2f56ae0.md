## Source intent
GLM-5.2 with a large context + thinking + tool_stream can return
HTTP 200 with a cleanly-closing SSE but `finish_reason=network_error`
(AI SDK normalizes this to `"other"`) and no content/reasoning/tool deltas.
The processor previously treated that empty completion as a normal end,
wrote it to the DB, and the active-goal machinery kept injecting
`system_continue`, producing an endless loop. The fix:
1. `processor.ts` finish-step detects, before setting
   `assistantMessage.finish`, that `finishReason === "other"` AND no
   text/reasoning/tool output was produced this round, and throws a
   retryable `MessageV2.APIError`. Success → normal retry; exhaustion →
   halt sets error → process returns "stop" → loop breaks.
2. `message-v2.ts` `fromError` gains an `APIError.isInstance` passthrough so
   the pre-classified APIError keeps its `isRetryable` classification instead
   of degrading to non-retryable `UnknownError` (which would bypass
   SessionRetry).
3. `prompt.ts` goal continuation adds a defensive `!lastAssistant.error`
   guard (normal control flow already returns "stop" on error; this prevents
   future control-flow changes from mistaking an errored assistant as
   continuable).
4. Tests: fromError passthrough (message-v2.test.ts) + 3 live processor
   effect tests (empty network_error → retry + recover; partial output +
   network_error → no throw; empty stop → no throw).

## Key target-adaptation decisions (verified against state 0397 code)
1. **Reason vocabulary.** Source checks `value.finishReason === "other"` (AI SDK
   normalization). The target's shared `LLMEvent.StepFinish` carries
   `reason: FinishReason` where `FinishReason =
   ["stop","length","tool-calls","content-filter","error","unknown"]`
   (packages/llm/src/schema/ids.ts:39). Both runtime paths normalize
   `network_error` to `"unknown"`: the AI SDK adapter maps any value outside
   the literal union to "unknown" (`ai-sdk.ts:21-23`, AI SDK's "other" is not
   in the union), and native protocols end with `mapFinishReason(...) →
   "unknown"` (`openai-chat.ts:378-384`). Adaptation:
   `value.reason === "unknown"` with an explanatory comment; both paths
   converge on the same trigger, preserving source intent.
2. **Error class.** Source throws `new MessageV2.APIError({...})`. The target's
   message-v2.ts only *imports* APIError from `@opencode-ai/core/v1/session`
   (not re-exported in the MessageV2 namespace), and the retry gate matches on
   `SessionV1.APIError.isInstance` + `error.data.isRetryable`
   (`retry.ts:74-81`). Adaptation: `throw new SessionV1.APIError({ message,
   isRetryable: true })` — same class (NamedError.create "APIError" with
   schema `{ message, statusCode?, isRetryable, responseHeaders?, responseBody?,
   metadata? }`), same retry semantics (`retry.ts` retries isRetryable errors
   with or without statusCode; our thrown error has no statusCode → retried).
3. **Handler placement (structural difference).** The target's event switch is
   organized differently from the source pre-image:
   - `hasReasoning`: set in the `reasoning-start` case right after the
     duplicate-guard, before the reasoningMap entry — mirror of the source
     position.
   - `hasToolCall`: source sets it inside the `tool-call` case before the part
     update; the target's `tool-call` case delegates part creation to
     `ensureToolCall`, so the flag is set right after `yield*
     ensureToolCall(value)` and before `logPartStart` — same case, same
     semantics (any tool output in this round counts).
   - `hasText`: set at the top of the `text-start` case, before
     `ctx.currentText = {...}` — mirror of the source position.
   - Empty-completion throw: target's `step-finish` case sets
     `ctx.assistantMessage.finish = value.reason`; the check is inserted
     between `Session.getUsage(...)` and that assignment — identical ordering
     guarantee (throw happens before the finish is persisted).
   - Retry reset: the target re-executes the whole inner block (which resets
     `ctx.currentText`/`ctx.reasoningMap`) under `SessionRetry.retry`; the
     three flag resets are added adjacent to those resets so a stale flag
     from the failed first attempt cannot suppress the detection on retry.
4. **fromError passthrough.** Inserted as a new switch case after the
   `OutputLengthError.isInstance` case (the closest "already-classified
   pass-through" sibling) and before `LoadAPIKeyError.isInstance`:
   `case APIError.isInstance(e): ... return e.toObject()`. `NamedError`
   instances expose `.isInstance` and `.toObject()` (core/src/util/error.ts),
   and `.toObject()` yields `{ name: "APIError", data: { message, isRetryable,
   ... } }` — exactly the shape the tests assert.
5. **prompt.ts guard.** The target's goal-continuation condition
   (`lastAssistant?.finish && !["tool-calls"].includes(...) && !hasToolCalls
   && lastUser.id < lastAssistant.id`, prompt.ts:1488-1493) matches the source
   pre-image; `!lastAssistant.error &&` is inserted after
   `lastAssistant?.finish &&` verbatim with the 3-line source comment.
6. **Tests.** Both test files append the source blocks nearly verbatim with
   two substitutions: `new MessageV2.APIError(...)` → `new
   SessionV1.APIError(...)` (test file already imports SessionV1), and
   `satisfies MessageV2.User` → `satisfies SessionV1.User` (matching the
   target's existing processor-effect.test.ts shape). The empty-completion SSE
   (`finish_reason: "network_error"`) is unchanged — the target harness
   (`test/lib/llm-server.ts` `raw({head,tail})`, `reply().text().stop()`,
   `llm.calls`) is byte-compatible with the source helper. Comment text
   documents the "other"→"unknown" normalization so future readers can trace
   the mapping.
