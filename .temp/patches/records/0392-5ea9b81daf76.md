## Source intent

修复 0350 引入的 consecutive-error breaker 的并行误触发：

**根因**：`consecutiveErrorMap` 的 value 是纯 `number`，仅按 toolName 聚合。
同一 assistant message 内的并行 tool-error（如 3 个 read 读不同路径全部
失败）会在一个批次内把 count 累加到 3，误触发 doom_loop permission ask 阻断
流——此时模型尚未看到错误结果，谈不上"改变策略"。

**修复**：value 从 `number` 改为 `{ count, lastMessageID }`：

1. `lastMessageID` 与 `ctx.assistantMessage.id` 相同（同一批次并行 error）→
   count 不递增；不同（跨 turn 的新失败）→ count += 1 并更新 lastMessageID。
2. 成功路径 delete 整个 entry（reset 语义不变）；触发 doom_loop 后
   `entry.count = 0` 而 lastMessageID 保留（同批次后续 error 不再触发，
   下一 turn 从 1 重新计数）。
3. 跨 turn 3 次连续 error 仍触发（既有正确行为不变），metadata 的
   `consecutiveErrors` 从 `errMap[toolName]` 改为 `entry.count`。

新增 2 个行为级测试：

- **same-batch 测试**：`failingRead` 工具（execute 恒 throw）+ `raw()`
  手工构造 3 个不同 tool.index 的 SSE chunks（reply().tool() 硬编码
  index=0 无法并行）→ 同一 process() 内 3 个并行 read 全 fail →
  断言 "continue" 且 error undefined（不触发）；
- **cross-turn 测试**：3 个独立 turn 各 1 个 read fail（不同 assistant
  message id）→ 第 3 个 turn 触发 doom_loop，deny 配置下
  permission.ask 抛 DeniedError → halt → "stop" + error 已定义（回归守卫）。

测试配置 `denyDoomLoopConfig` 用 `config.permission.doom_loop = "deny"` 覆盖
agent 默认的 "ask"。
