## Port decision summary

Bring voice input (alt+v / f8) to the two dialog-style prompt surfaces by reusing the existing
`createVoiceInputController` plus the `prompt.voice.toggle` keybind — zero new configuration
surface. The upstream commit modified three files under the old TUI tree
(`packages/opencode/src/cli/cmd/tui/…`); in this replay series the TUI was migrated to
`packages/tui/…` (see prior batches), so every path was remapped:

- `packages/opencode/src/cli/cmd/tui/routes/session/question.tsx` → `packages/tui/src/routes/session/question.tsx`
- `packages/opencode/src/cli/cmd/tui/ui/dialog-prompt.tsx` → `packages/tui/src/ui/dialog-prompt.tsx`
- `packages/opencode/test/cli/tui/prompt-voice-input.test.ts` → `packages/tui/test/prompt/prompt-voice-input.test.ts` (already present per prior batches)

Semantic changes, in order of safety-criticality:

1. DialogPrompt:
   - Import `useRenderer` (`@opentui/solid`), `onCleanup` (solid-js), `useToast`, `PromptVoiceInput`, `PromptVoiceRecorder`.
   - Voice controller block after `let textarea`: `voiceInputStatus` signal, `voiceInputBusy`,
     `voiceShortcut` (`useCommandShortcut("prompt.voice.toggle")`), darwin `f8` / else `alt+v`
     fallback, `insertVoiceText` guarded by `textarea.isDestroyed` with a next-tick layout dirty
     + `renderer.requestRender()` (mirrors the main Prompt behavior),
     `createVoiceInputController({ transcriber, startRecorder, insertText, onStatus, onError→toast })`.
   - `onCleanup(() => void voiceInput.abort())` — releases the native PvRecorder process on
     ESC / dialog.clear / dialog.replace, otherwise the mic hangs until the 90s transcribe timeout.
   - Submit protection: `confirm()` now bails when `voiceInputBusy()` so Enter cannot submit the
     pre-transcription draft (transcription runs up to 90s).
   - Voice toggle `useBindings` (target-gated on `textareaTarget`, disabled while `props.busy`) so
     all DialogPrompt consumers (Goal create/edit, Session rename, Provider config, Plugin API)
     get the same `prompt.voice.toggle` muscle memory.
   - Footer: recording status (red dot + timer + stop shortcut; spinner while transcribing) and
     the `alt+v voice` hint when a transcriber is configured; hint hidden while busy to avoid
     duplicating "f8 stop".

2. QuestionPrompt:
   - Imports: `createEffect`, `on` (solid-js), `useCommandShortcut` (keymap), `useToast`,
     `PromptVoiceInput`, `PromptVoiceRecorder`, `Spinner`.
   - Same controller block plus the QuestionPrompt-specific lifecycle rules:
     - `createEffect(on(() => store.editing, …), { defer: true })` aborts an in-flight recording
       when the user leaves edit mode (ESC/option switch) — the custom-answer textarea is then
       already destroyed and transcription would be discarded. `defer: true` avoids a meaningless
       mount-time abort.
     - `insertVoiceText` re-guards `textarea.isDestroyed` against the stale ref left by `<Show>`.
     - Return-key submit path blocks on `voiceInputBusy()` (pre-transcription draft protection).
   - Voice toggle `useBindings` scoped to `QUESTION_MODE` and `store.editing && !confirm()` —
       adapted to the file's mode-stack binding convention (upstream used unscoped bindings).
   - Footer: recording status + `alt+v voice` hint, shown only while editing.

3. Tests: three controller regression tests appended inside the `describe("prompt voice input", …)`
   (verbatim from source):
   - "abort is idempotent when called from both onCleanup and createEffect" — double-abort must be
     a no-op (recorder aborted exactly once).
   - "does not invoke insertText after abort during in-flight transcription" — late transcription
     results must not write into destroyed textareas (generation bump guarantee).
   - "insertText receives the full transcribed text for consumer-side guards to check" — the
     normal path still delivers the full transcript to the consumer-side `isDestroyed` guard.

The state file for question.tsx already carried later-ported features (mode-stack `QUESTION_MODE`,
`useOpencodeModeStack`, `../../config` import path), so the bindings were adapted to that
convention instead of the upstream plain-bindings shape. `useBindings` in dialog-prompt.tsx also
differs from upstream (target/priority-based), so the voice toggle binding was written in the
file's native shape.
