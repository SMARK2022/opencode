## Source intent

修复 ESC×2 取消 agent loop 时"取消延迟 1-2s + 新命令被误杀"两个问题：

- **根因 1：bash 工具 kill 路径无 SIGKILL 升级上限**。`handle.kill(
  { forceKillAfter: "3 seconds" })` 在 Unix 上是 no-op——forceKillAfter 只
  限制信号发送（killProcessGroup 同步即完成），不限制
  `Deferred.await(exitSignal)` 的进程退出等待（无上限）。进程收 SIGTERM 后
  需数秒退出时 kill 无限阻塞。
  **Change 1**：替换为 `handle.kill().pipe(Effect.timeoutOrElse({duration:
  "500 millis", orElse: () => handle.kill({ killSignal: "SIGKILL" })
  .pipe(Effect.ignore)}), Effect.orDie)`——真实 SIGTERM→500ms→SIGKILL 序列；
  orElse 的 ignore 处理 SIGTERM 后恰好退出时的 ESRCH。abort 与 timeout 两条
  路径都替换。
- **根因 2：4s settle 超时被无上限 kill 撑大**。**Change 2**：
  `ABORTED_TOOL_SETTLE_TIMEOUT` "4 seconds"→"2 seconds"（bounded kill 后
  tool 最多 500ms kill + ~500ms drain = 1s，2s 给 100% 安全边际；per-tool
  并行不串行累加）。
- **根因 3：cancel 的 TOCTOU**。state.cancel（设 Idle + 阻塞
  Fiber.interrupt）在 abortPendingAssistants 之前执行，两步之间新 prompt
  可启动，新 assistant 被误终态化为 Aborted。**Change 3**：cancel 在
  state.cancel 前快照 pending assistant IDs（MessageV2.stream 同步生成器，
  快照原子），abortPendingAssistants(sessionID, pendingIds) 按快照过滤；
  子会话递归不传 pendingIds。
- **根因 4：cancelBackgroundJobs 串行**。**Change 4**：run-state.cancel
  用 `Effect.all(..., {concurrency: "unbounded", discard: true})` 并行执行
  cancelBackgroundJobs 与 existing.cancel（无 runner 分支并行 jobs + 置
  idle）。
- 新增 113 行设计文档 docs/abort-latency-fix-plan.md；prompt.test.ts 新增
  1 个竞态回归测试（hang → fork cancel → 立即提交新命令 → 断言新 assistant
  无 MessageAbortedError）。

## Notes / deviations from source

- **快照 API 差异**：source 用 `MessageV2.stream`（同步生成器、原子快照），
  target 用 `sessions.messages`（effect 调用、含 hidden 过滤后的可见序列）。
  语义等价性：两者都枚举"当前可见消息"，且快照都在 state.cancel 前完成；
  target 版本在 filter 前多了 catch 兜底（若 messages 失败按空快照处理，
  cancel 收口不受阻——与 abortPendingAssistants 内部既有一致）。
- **cancel 分支差异**：source `!existing || !existing.busy` 置 idle；target
  仅 `!existing`。保留 target 形态（Runner 的 busy 状态机在 target 由
  onIdle/onBusy 回调管理，cancel 场景无差异），并行化语义不受影响。
- handler 端（prompt/shell 等）不做本次改动——abort 竞态修复在 prompt.ts
