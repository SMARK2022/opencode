## 深入分析：超时受控截断设计
- 目标 grep 返回 `readonly Match[]`（上游 API）——超时信息不能放进返回值，否则破坏上游调用方。
- 适配方案：GrepInput 增加 `onTimedOut?: () => void` 回调，run() 在超时置位时同步调用。
- grep tool 用回调设置局部 timedOut 标志；空结果 + timedOut 时输出 "Search timed out after N ms" 而非 "No files found"。
- 超时 killer：forkScoped sleep → timedOut=true + onTimedOut() → handle.kill({ forceKillAfter: "3 seconds" })——与 shell 工具同一 3 秒升级窗口。
- 半行 JSON 容错：timeout 可能在 rg 写出最后一行 JSON 中途杀进程；timedOut 时 parse 错误被吞，非超时解析错误仍上抛。
- 正则错误保留：timedOut 且无匹配且 stderr 含 regex parse error 时仍返回失败——超时不能伪装成成功。

## 为什么 maxFiles: false
- 源 244 用真实执行时间做保护，不再用候选文件数粗暴拒绝。
- 5001 个空文件的仓库搜索应快速完成返回真实匹配；低命中大搜索由 timeout 受控终止。
- 目标 grep tool 传入 `maxFiles: false` 禁用候选上限（#138 的 SearchTooBroadError 逻辑保留给其他调用方）。
