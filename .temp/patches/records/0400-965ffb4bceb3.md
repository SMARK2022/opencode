## Source intent
The `setup-bun` composite action's three `bun pm cache` steps (Get cache
directory / Restore / Save) get `runner.os != 'Windows'` guards. On GitHub
Windows runners, `actions/cache`'s tar+zstd restore of the 634MB cache
measured ~209s — slower than bun's native extract-to-cache (~168s) — and the
save step then loses a further ~43s in save races (bun.lock changes on every
commit → exact key never hits → all 5 Windows jobs race to save). Cold
install (~224s on build-opencode Windows) beats cached (304s). macOS/Linux
restore is only 16-67s, so their caching is preserved. The Save step
condition also moves `runner.os != 'Windows'` to the FRONT for short-circuit
correctness: on Windows the restore step (`id: bun-cache`) is skipped, its
`cache-hit` output does not exist, and an unguarded `cache/save` would run
with an empty path.
