# 修复缓存测试与进程清理的不稳定问题

## 范围

基于 `a012050340b7eeed68488018205f2ed4cf8d4f0f`，处理两项已出现的必过测试失败：

- macOS：2048-turn 缓存测试比较一次完整请求的冷暖耗时，把模型响应和持久化波动算成缓存问题。
- Windows：换主测试在清理 replacement 进程时报 ESRCH，进程已经不存在。

不修改 warning-only 测试，不增加超时或放宽既有性能预算。

## 修改

1. 在现有 LLM 输入入口验证 4096 条历史消息的内容和转换对象复用，并检查新请求包含前次响应与新输入。保留原有的一秒准备预算和 full-hit 性能比较。
2. 修复统计查询中的重复扫描：相关子查询使用已经存在的 Message 索引，避免对每个 Assistant 再扫描整段 Session 的 Part。保留全部过滤、样本数、恢复预算、事务和水位规则。
3. 让测试直接创建并持有 original、replacement 两个进程。replacement 仍由认证 shutdown 事件触发；原进程退出后，新进程必须继续存活。清理使用 Bun 已有的进程句柄及退出信号，不再从锁文件反查 PID 后结束进程。

没有新增生产接口、依赖、配置或数据库迁移，也没有新增吞错逻辑。

## 证据与验证

- 给第二次模型响应增加延迟时，旧耗时比较失败，但 4096 个历史转换对象仍被复用。新断言通过；关闭真实缓存时，新复用断言失败。
- 同一统计查询的实际执行计划原先按 Session 查 Part。仅约束已有 Message 索引后，隔离测量从约 731–785 ms 降至约 6 ms，返回结果相同。这是独立的真实成本，不意味着它是 macOS 时间倒置的唯一原因。
- SQL 回归解释真实查询的访问范围，并保留统计结果、隐藏规则与冷存储断言。它在原代码上失败，修复后通过。
- Windows 的非 detached replacement 原先属于 original 的进程 job。测试改为直接持有两个句柄，保留换主后拒绝强停的全部断言，并验证 original 退出后 replacement 仍活着及重复清理。
- Linux 隔离实验和实际 CLI 用例不代替 Windows 原生验证；最终以本 PR 精确提交的跨平台 CI 为准。
